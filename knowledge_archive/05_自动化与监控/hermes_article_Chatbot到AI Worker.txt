标题: 从 Chatbot 到 AI Worker：我是如何把 Hermes 改造成 24 小时 AI 工作台
Article ID: 7668613817527910946

过去两年，大模型最大的变化不是回答问题越来越准，而是开始进入任务执行阶段。 但绝大多数 AI 使用方式仍停留在： 打开窗口 → 输入问题 → 等待回答。
这种模式本质仍然是“增强搜索”。 真正的 Agent 应该像一个数字员工：
知道自己的职责；
拥有固定工作环境；
能够主动接收任务；
按照流程执行；
输出可验证结果；
留下完整记录。
因此，我开始尝试把 Hermes 从聊天工具改造成一个 24 小时运行的 AI 工作台。 很多人第一次用 Hermes，都会先做同一件事：打开聊天窗口，问它一个问题，再等它返回答案。
这只能证明 Hermes 会调用工具。

真正的改造，是把“等我提问”改成“任务自己进来、按规则执行、结果自动交付、过程还能被追踪”。
怎么把一次性聊天拆成可重复任务；
怎么让任务在固定目录、固定角色、固定方法里运行；
怎么用 Cron 和 Webhook 把“定时发生”和“事件发生”接进来；
怎么把结果写回文件、消息或代码协作流程；
怎么避免一个拥有终端权限的 Agent 变成无人值守的事故入口。

一、先换一个设计目标：不是“更强的聊天”，而是“可持续的任务系统”
聊天机器人通常只有一条链路：
用户输入 → 模型回答AI 工作台至少要有五个部分：
任务入口 → 任务编排 → Agent 执行 → 结果交付 → 运行治理这五部分缺一不可。
没有入口，Agent 只能等人提问；没有编排，任务每次都从零开始；没有执行，输出停留在文字；没有交付，结果还得人工复制；没有治理，自动化越多，风险越大。
Hermes 的价值，不是把这些能力分散在几个命令里，而是可以把它们接成一条持续运行的链路：
Gateway 负责让入口常驻；
Cron 负责按时间唤起任务；
Webhook 负责接收外部事件；
Profile 负责把不同角色的配置、记忆和会话隔离开；
Skill 负责把一次成功的做法固化下来；
工具、文件和消息平台负责把结果真正写出去。
改造的核心，不是“打开更多功能”，而是给每类任务补齐自己的运行协议。
二、第一步：先把“聊天”改造成“有边界的工作区”
很多 Agent 任务失败，不是模型不会做，而是它不知道三件事：
应该在哪个目录工作；
应该遵守哪套项目规则；
这次任务到底算不算完成。
因此，第一步不是接 飞书、微信，也不是配置十个 MCP，而是先固定工作边界。
1. 给任务一个真实的工作目录
例如，我们准备做一个“AI 技术情报工作台”：
mkdir -p /srv/hermes-workbench/{briefs,raw,logs}这个目录不只是放输出文件，还应该放项目级规则，例如：
/srv/hermes-workbench/├── AGENTS.md                 # 任务边界、输出格式、禁止事项├── briefs/                   # 最终简报├── raw/                     # 原始抓取结果└── logs/                    # 运行日志或失败记录AGENTS.md 里不要写“请认真完成任务”这种空话，而应该写可验收的约束：
# 工作台规则- 所有最终结果写入 briefs/，不得只在聊天里返回。- 每条信息必须保留来源链接。- 不确定的事实标记为“待核验”，不得改写成确定结论。- 没有新增内容时，最终响应只输出 [SILENT]。- 写入文件后必须重新读取，确认文件确实存在。这里的关键变化是：把提示词里的软要求，变成工作目录里的长期规则。
2. 用 --workdir 让 Cron 进入同一个现场
Hermes 的 Cron 默认在一个全新的 Agent 会话里运行，也不会自动继承你当前聊天的上下文。需要把项目目录显式传进去：
hermes cron create "0 9 * * 1-5" \  "读取指定信息源，筛选与 AI 工程实践有关的新内容，生成一份不超过 10 条的中文简报。每条包含：标题、来源、核心变化、对团队的影响、是否值得跟进。结果必须写入 briefs/daily-brief.md；没有新增内容时只输出 [SILENT]。" \  --name "工作日 AI 技术简报" \  --workdir /srv/hermes-workbench \  --deliver local这条命令真正完成了四个改造：
时间固定：工作日上午 9 点执行；
上下文固定：进入 /srv/hermes-workbench；
输出固定：写入项目目录，而不是只返回聊天气泡；
通知可控：使用 [SILENT] 抑制无变化时的噪音。
创建后不要等到第二天才验证：
hermes cron listhermes cron statushermes cron run <job_id>hermes cron runs --limit 20先手动触发一次，看三个外部事实：文件是否生成、内容是否符合格式、运行记录是否成功。
“模型说已经完成”不算完成，外部状态发生变化才算完成。
三、第二步：把一次性 Prompt 固化成 Skill
如果每天都要在 Cron 里写一大段任务说明，说明工作方法还没有被固化。
一个可复用的 Skill，至少应该回答五个问题：
什么时候触发？读取哪些输入？按什么步骤处理？什么结果算通过？失败后留下什么记录？以“技术简报”为例，Skill 不应该只是：
请帮我整理今天的 AI 新闻。而应该把方法写成类似下面的结构：
# 技术简报工作流## 触发条件收到“整理技术信息”“生成早报”或 Cron 调度时触发。## 处理步骤1. 只读取允许的信息源。2. 去掉重复内容和纯营销内容。3. 为每条内容补充“对工程团队的影响”。4. 无法核验的数字和案例标记待核验。5. 按固定模板写入 briefs/。6. 重新读取文件进行自检。## 通过标准- 有来源链接；- 每条都有工程影响；- 没有把猜测写成事实；- 文件成功写入；- 无变化时返回 [SILENT]。Cron 只负责“什么时候运行”，Skill 负责“怎么运行”。
这是一条重要边界：
Prompt 是一次任务的指令；
Skill 是一类任务的工作方法；
Memory 是跨任务需要保留的稳定事实和偏好。
把三者混成一段超长 Prompt，短期看省事，长期一定难维护。

四、第三步：把“固定时间”与“外部事件”拆成两条入口
24 小时工作台不能只有 Cron。
Cron 适合回答：
每天早上要做什么？每隔两小时要检查什么？Webhook 适合回答：
GitHub 有新的 PR 后要做什么？监控系统报警后要做什么？外部服务状态变化后要做什么？1. 用 Cron 做周期性工作
典型任务包括：
每日技术简报；
项目目录巡检；
定期汇总日志；
每周生成经营或研发报告；
只在文件发生变化时触发分析。
对于不需要模型判断的看门狗，不要强行调用 Agent。当前 CLI 支持 --no-agent 和 --script，可以让脚本直接输出结果，避免为“内存是否超过阈值”消耗一次推理：
hermes cron create "every 5m" \  --no-agent \  --script memory-watchdog.sh \  --deliver telegram \  --name "内存告警"能用脚本精确判断的事情，不要交给模型猜。
2. 用 Webhook 做事件驱动
例如，收到 GitHub Pull Request 后，先经过事件筛选，再交给代码审查流程：
hermes webhook subscribe github-pr \  --events "pull_request" \  --prompt "请处理 Pull Request：仓库 {repository.full_name}，标题 {pull_request.title}，作者 {pull_request.user.login}，动作 {action}。只输出审查结论、风险点和建议，不直接修改代码。" \  --skills "github-code-review" \  --deliver log \  --secret "$GITHUB_WEBHOOK_SECRET"然后查看动态订阅：
hermes webhook listWebhook 入口需要先通过 Gateway 配置启用。运行后可以检查：
curl http://localhost:8644/health真正重要的不是“接上了 Webhook”，而是入口后面必须有过滤链路：
收到事件  ↓验证签名  ↓判断事件类型  ↓过滤无关事件  ↓决定是否唤起 Agent  ↓执行低风险动作  ↓交付结果并留痕Webhook 的签名只能证明“请求来自持有密钥的一方”，不能证明 PR 标题、Issue 正文或提交信息是可信指令。外部文本依然是不可信输入。

五、第四步：用 Profile 拆出不同的工作角色
当写作、代码、研究和运维都挤在一个 Agent 里，问题不是能力不够，而是状态开始串台：
写作任务带入了代码项目规则；
研究任务继承了不必要的终端权限；
不同项目的记忆混在一起；
一个消息入口不知道该把任务交给谁。
可以用 Profile 做状态隔离：
hermes profile create researcher \  --description "读取文档和源码，整理研究结论"hermes profile create writer \  --description "按公众号工作流生成和审校技术文章"再分别设置工作目录：
hermes --profile researcher config set terminal.cwd /srv/hermes-researchhermes --profile writer config set terminal.cwd /srv/hermes-writingProfile 隔离的是 Hermes 自己的配置、记忆、会话、Skills、Cron 和 Gateway 状态，不是沙箱。
在默认本机终端后端里，Agent 仍可能拥有当前用户的文件权限。需要真正限制文件访问时，要使用 Docker、SSH 或其他隔离后端，而不能把 Profile 当成安全边界。
这是很多“AI 工作台”文章容易漏掉的地方：

> 角色隔离解决的是状态污染；沙箱解决的是权限越界。两者不是一回事。
六、第五步：给无人值守任务加上“验收协议”
自动化最容易失败的地方，不是触发，而是结果不可验证。
一条合格的无人值守任务，至少要包含下面这五个字段：
字段
要回答的问题
输入
这次任务读什么？
处理
Agent 允许做哪些动作？
输出
结果写到哪里、发给谁？
通过
什么状态才算成功？
失败
出错后留下什么记录？
例如，不要只写：
每天检查项目状态并告诉我结果。应该改成：
检查 /srv/project 的 Git 状态、最近一次测试结果和未提交文件。只允许读取和汇总，不修改代码。结果写入 /srv/hermes-workbench/briefs/project-status.md。如果没有异常，只返回 [SILENT]。如果有异常，必须列出文件、命令输出摘要和建议动作。这会直接影响系统的可靠性：
任务从“开放式聊天”变成“有输入和输出的作业”；
模型从“自由发挥”变成“在协议内完成动作”；
人从“凭感觉看答案”变成“检查文件、日志和运行记录”。
七、权限要按任务拆，不要按“我信不信模型”拆
我建议把自动化任务分成三层。
第一层：可以自动完成
读取公开资料；
汇总日志；
检查 Git 状态；
生成 Markdown 草稿；
写入工作区文件；
发送内部提醒。
第二层：自动准备，人来确认
创建工单；
发布文章草稿；
提交 Pull Request；
修改项目配置；
向外部客户发送消息。
第三层：默认不做无人值守
删除数据；
修改权限；
生产部署；
付款、退款和转账；
批量修改外部系统；
发送带有法律或商业承诺的内容。
Webhook、网页、邮件、Issue 和文档里的文字，都可能携带间接提示注入。真正的防线不是“把 Prompt 写得更长”，而是：
缩小工具集限制工作目录保留审批隔离运行时记录每次执行如果一个 Webhook 任务只需要读取 PR 并生成审查意见，就不要给它付款、删除、改权限和生产部署能力。
八、WSL 上的“24 小时”不是一句宣传语
在 WSL 里，Gateway 前台运行是最容易验证的方式：
hermes gateway run测试稳定后，再考虑：
hermes gateway installhermes gateway starthermes gateway status但 WSL 本身不是一台天然 24 小时在线的服务器。Windows 休眠、WSL 实例退出或网络变化，都可能让 Gateway 和 Cron 一起停止。
所以实际选择应该是：
个人试用：WSL 前台运行，先跑通一条任务链；
长期无人值守：放到稳定的 Linux VPS 或服务器；
生产使用：补上日志、备份、告警、权限和回滚。
创建了 Cron，不代表任务会执行；Gateway 在线、任务状态正常、运行记录成功，才代表链路真的活着。
九、我会按这个顺序完成改造
如果从零搭建，不要一次把所有能力打开。我会按下面的顺序：
第 1 步：固定一个工作目录和输出文件第 2 步：用一次性 Prompt 跑通一个低风险任务第 3 步：把稳定方法沉成 Skill第 4 步：把任务挂到 Cron，并手动触发验收第 5 步：接入一个 Webhook，只处理低风险事件第 6 步：用 Profile 拆写作、研究、代码等角色第 7 步：收紧工具、权限、审批和运行目录第 8 步：再把 Gateway 交给长期运行环境每一步都要留下可检查的东西：
文件；
运行记录；
消息投递；
Webhook 返回状态；
失败日志；
人工确认点。
写在最后：工作台的价值，是让任务持续向前
未来企业里的 AI，不会只是一个聊天窗口。
它更像一组数字员工：
有岗位； 有流程； 有权限； 有工作空间； 有考核记录。
Hermes 只是一个例子。
真正重要的是，我们开始从“使用 AI”，进入“管理 AI 工作流”的阶段。
而一个真正有用的 AI 工作台，不是模型什么都能做，而是它能在明确边界内，持续、可验证地把一类事情做完。
