# Code Review — 五轴质量门禁

> **审批标准：** 当变更**明确改善了整体代码健康度**时就批准，即使它不完美。完美代码不存在 — 目标是持续改进。

## Communication Style

* **语言**：中文为主，技术术语保留英文原文
* **结构**：先给结论（PASS/NEEDS\_FIX/BLOCKED），再展开五轴细节
* **语气**：专业直接，不回避问题，但避免居高临下
* **受众**：代码作者和审查者都能看懂，不假设对方是专家
* **禁忌**：不写"建议考虑"等模糊表述，直接说"应该怎么做"

## Success Criteria

- [ ] 五轴全部给出明确评级（✅/⚠️/❌），无遗漏

- [ ] 每个发现标注严重度（🔴严重/🟡警告/🟢建议）

- [ ] Verdict 明确：PASS / NEEDS_FIX / BLOCKED

- [ ] 给出了"下一步最小动作"——今天能做的具体一条

- [ ] 阻塞性问题没有遗漏（安全漏洞、数据丢失风险）

## When to Use

* 用户说"审查代码"、"review this"、"代码评审"、"审查这个PR"
* 合并 PR 前的质量把关
* 功能实现完成后的自我审查
* 评估他人代码质量
* 重构或 bug 修复后的验证
* **"检查源代码准确度"、"验证代码缺陷"、"是否达到设计要求"** → 触发下方 **项目级验证模式**

**不要触发于：** 纯写作、需求分析、部署操作、非代码类任务。

## 项目级验证模式（Project-Level Verification）

> 与 PR 审查不同：PR 审查关注**增量变更**，项目级验证关注**整个代码库的完整性、准确性和设计符合度**。
> 触发词："检查源代码准确度"、"验证有没有缺陷"、"是否达到设计要求"、"整体验证评估"。

### 验证流程（6步）

```
Step 1: 语法检查（全量）
  → python3 -m py_compile 逐文件检查，或 ast.parse 批量扫描
  → 记录：通过数/失败数/修复数

Step 2: 模块功能验证
  → 检查每个模块的核心类/方法是否存在、签名是否正确
  → 用 inspect 或 AST 解析，不依赖 import（避免依赖缺失）
  → 记录：模块数/类数/方法数

Step 3: 端到端测试
  → 运行已有测试套件，记录通过率
  → 如无测试，手动构造最小调用链验证核心功能
  → 记录：通过/失败/跳过

Step 4: Bug 发现与修复
  → 结合语法检查和功能验证中发现的问题，逐一修复
  → 修复后重新验证，确保不引入新问题
  → 记录：发现数/修复数/遗留数

Step 5: 架构与文档验证
  → 对照设计文档/技术方案，检查模块覆盖度
  → 检查文档完整性（README、API 文档、专利文件等）
  → 检查部署配置（Docker、requirements、脚本等）
  → 记录：符合度百分比

Step 6: 生成验证报告
  → 输出结构化报告：评分维度表 + 发现列表 + 设计符合度对照 + 建议
  → 报告保存到项目 docs/ 目录
  → 可选：上传到云端备份
```

### 验证报告模板

```markdown
# [项目名] 源代码验证评估报告

## 验证总结（评分维度表）
| 维度 | 评分 | 说明 |
|------|------|------|
| 代码质量 | X% | ... |
| 功能完整性 | X% | ... |
| 架构设计 | X% | ... |
| 测试覆盖 | X% | ... |
| 文档完整性 | X% | ... |
| 部署就绪度 | X% | ... |
| **总体评分** | **X%** | **结论** |

## 发现并修复的Bug
| # | 位置 | 问题 | 修复方案 | 状态 |

## 设计要求符合度（对照设计文档逐项检查）
| 设计要求 | 实现状态 | 符合度 |

## 建议下一步
```

### 关键 pitfall

* **不要只跑语法检查就报告"通过"** — 语法正确 ≠ 功能正确，必须走完6步
* **不要跳过端到端测试** — 单元测试通过不代表模块间集成正确
* **验证报告要保存到项目 docs/ 目录** — 不能只输出到聊天就结束

## Prerequisites

- [ ] 有变更的代码文件可读（本地文件、PR diff、或用户粘贴的代码片段）

- [ ] 知道变更的上下文（PR 描述、issue 链接、或用户说明）

- [ ] 能运行项目的构建/测试工具（如果验证需要）

如果代码片段不完整或上下文缺失，**停下来问用户要什么**，不要猜。

## Procedure

### Step 1: 确定审查范围

确认你要审查的是什么：

* **PR diff**：通过 `gh pr diff <number>` 或 GitHub API 获取
* **本地变更**：`git diff HEAD~1` 或 `git diff main`
* **指定文件**：用户提供的文件路径或代码片段
* **整个文件**：用户指定的完整文件

```bash
# 如果是 GitHub PR
gh pr diff <number>

# 如果是本地最近提交
git diff HEAD~1 --stat   # 先看变更概览
git diff HEAD~1          # 再看具体 diff
```

看什么：变更文件数量、每个文件的行数增减。如果超过 **1000 行**或 **10+ 文件**，提醒用户变更过大，建议拆分审查。

### Step 2: 五轴逐项审查

按以下五个维度**逐项**审查，每个维度给出评级（✅通过 / ⚠️警告 / ❌失败）：

#### 轴 1: 正确性（Correctness）

```bash
# 检查清单（逐项打勾）
```

- [ ] 代码匹配规格/任务需求（不是做了别的事）

- [ ] 边界情况处理了（null、空值、边界值、极端输入）

- [ ] 错误路径处理了（不只是 happy path）

- [ ] 测试存在且测试了正确的东西

- [ ] 无 off-by-one、竞态条件、状态不一致

**关键命令：**

```bash
# 如果有测试
npm test 2>&1 | tail -20
# 或
pytest -x -q 2>&1 | tail -20

# TypeScript 类型检查
npx tsc --noEmit 2>&1 | head -30
```

#### 轴 2: 可读性 & 简洁性（Readability）

- [ ] 命名具有描述性（无 temp、data、result 等无上下文命名）

- [ ] 控制流直接（无嵌套三元表达式、深层回调）

- [ ] 无过度"聪明"的技巧

- [ ] 无死代码（无操作变量、向后兼容垫片、// removed 注释）

- [ ] 1000 行能搞定的事没写成 100 行

- [ ] 抽象配得上其复杂性（不要到第三次使用时才抽象）

**关键命令：**

```bash
# 检查文件长度
wc -l <changed-files>

# 搜索可疑模式
grep -rn "TODO\|FIXME\|HACK\|XXX" <files> 2>/dev/null | head -10

# 检查未使用的 import
npx eslint <files> --no-error-on-unmatched-pattern 2>&1 | grep "unused\|no-unused"
```

#### 轴 3: 架构（Architecture）

- [ ] 遵循现有模式或引入了有正当理由的新模式

- [ ] 模块边界清晰（无循环依赖）

- [ ] 无应该共享的重复代码

- [ ] 依赖方向正确

- [ ] 不过度工程化、不过度耦合

**关键命令：**

```bash
# 检查循环依赖（如果是 Node.js）
npx madge --circular <entry-file> 2>&1

# 检查重复代码
npx jscpd <src-dir> 2>&1 | head -20
```

#### 轴 4: 安全性（Security）

```bash
# 搜索硬编码密钥（必做）
grep -rn "SECRET\|PASSWORD\|API_KEY\|TOKEN\|PRIVATE_KEY" <files> 2>/dev/null | grep -v "\.env" | grep -v "process\." | head -10
```

- [ ] 用户输入经过验证和清理

- [ ] 密钥远离代码、日志和版本控制（无硬编码）

- [ ] 认证/授权检查到位

- [ ] SQL 查询参数化（无字符串拼接）

- [ ] 输出编码防止 XSS

- [ ] 依赖项来自可信来源

**关键命令：**

```bash
# 依赖漏洞扫描（Node.js）
npm audit --production 2>&1 | head -30

# Python 安全扫描
bandit -r <python-files> 2>&1 | head -20
```

#### 轴 5: 性能（Performance）

- [ ] 无 N+1 查询模式

- [ ] 无无界循环或不受约束的数据获取

- [ ] 异步操作正确使用

- [ ] UI 组件无不必要的重新渲染

- [ ] 列表端点有分页

- [ ] 热路径无大对象创建

**关键命令：**

```bash
# 检查 N+1 查询（ORM 相关）
grep -rn "\.forEach.*\.find\|for.*\.query" <files> 2>/dev/null | head -10

# 检查无界获取
grep -rn "SELECT.*LIMIT\|fetch.*page\|all()" <files> 2>/dev/null | head -10
```

### Step 3: 变更大小评估

```
~100 行变更 → 好。一次可审查完。
~300 行变更 → 可接受，如果是单一逻辑变更。
~1000 行变更 → 太大。建议拆分审查。
```

**"一个变更"的定义：** 一个自包含的修改，处理一件事，包含相关测试，提交后系统保持功能正常。
