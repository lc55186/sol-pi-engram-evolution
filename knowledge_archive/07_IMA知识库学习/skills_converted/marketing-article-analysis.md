# marketing-article-analysis

> 对云厂商/营销类推广文章进行结构化批判性分析，识别本质、对比自身架构、提取自曝短板、评估风险，输出采纳/不采纳结论。适用于百炼 CLI、Dify、Coze、LangChain Cloud 等云厂商工具评估。

# 营销文章结构化分析

## 触发条件

* 用户发送云厂商/营销类推广文章要求分析
* 收到"这个怎么样"、"值不值得用"、"分析一下"等评估请求
* 看到 GitHub Trending / Hacker News 上的云厂商新品

**不适用于**：纯技术教程、学术论文、开源项目 README、非营销性质的技术博客。

## 核心工作流（5 步）

### Step 1: 本质识别

回答：这篇文章到底是什么？

* 是软文推广、技术深度分析、还是产品发布？
* 发布方是谁？（云厂商/独立开发者/媒体？）
* 目标受众是谁？（开发者/企业决策者/投资者？）
* "开源"是否属实？（开源 SDK 不等于开源服务）
* "GitHub Trending"是否真实？（短期刷榜 vs 长期热度）

### Step 2: 与自身架构对比

| **维度** | **对方方案**    | **Hermes（我们）** | **差异** |
| ------ | ----------- | -------------- | ------ |
| 部署模式   | 云端/本地/混合    | 自托管            | ⚠️/✅   |
| 模型支持   | 单一平台/多平台    | 多提供商           | ⚠️/✅   |
| 离线能力   | ❌/✅         | ✅              | ⚠️/✅   |
| 数据安全   | 出域/不出域      | 不出本机           | ⚠️/✅   |
| 定制能力   | API 限制/源码可控 | 全可扩展           | ⚠️/✅   |
| 成本结构   | 按量付费/免费     | 自备 Key         | ⚠️/✅   |

### Step 3: 提取文章自曝短板

营销文章中**主动承认**的痛点 = 最真实的竞争劣势分析。这些通常是：

* "当前版本缺少 X" → 说明 X 是刚需但尚未实现
* "希望未来支持 Y" → Y 是用户期望方向
* "Z 有待完善" → Z 是当前最大短板

将自曝短板与自身已解决的问题对照 → 验证自身优势。

### Step 4: 警惕点分析

识别文章中的**误导性话术**：

| **陷阱类型** | **示例**             | **真相**              |
| -------- | ------------------ | ------------------- |
| "开源"陷阱   | Apache 2.0 开源 SDK  | 后端服务闭源，必须联网         |
| "热榜"陷阱   | GitHub Trending #1 | 短期运营结果，不代表技术领先      |
| "降低门槛"陷阱 | 一条命令搭建 AI 智能体      | 降低的是入门门槛，提高的是迁移门槛   |
| "完全自由"陷阱 | 协议合规可自由使用          | 自由地写了调用代码，但运行需付钱给厂商 |
| "生态绑定"陷阱 | 标准化命令              | 一旦依赖该 API，切换成本极高    |

### Step 5: 输出结论

```markdown
## 分析结论：[采纳 / 不采纳 / 部分采纳]

### 核心价值
- [1-3 条真正有价值的点]

### 不可接受的风险
- [1-3 条核心冲突点]

### 结论
一句话总结：为什么值得/不值得投入资源。
```

## 用户偏好嵌入

* **结论先行**：第一行直接给出"采纳/不采纳"结论
* **对比表格**：必须包含与自身架构的维度对比
* **引用原文**：文章自曝的短板要标注原文位置
* **不编造数据**：Stars 数、Trending 排名等需核实或标注"待验证"
* **中文为主**：技术术语保留英文原文

## Pitfalls

| **坑**         | **症状**    | **Fix**                   |
| ------------- | --------- | ------------------------- |
| 把软文当技术分析      | 只总结内容不批判  | 必须执行 5 步完整流程              |
| 忽略发布方利益       | 未指出"谁在受益" | 第一步就识别发布方动机               |
| 过度贬低竞品        | 结论偏激无依据   | 每个批评点必须有事实支撑              |
| 遗漏自曝短板        | 只分析优点     | 第 3 步专门提取文章承认的痛点          |
| 混淆"功能"和"架构理念" | 比较表面功能差异  | 第 2 步聚焦架构级对比（部署/模型/数据/成本） |
