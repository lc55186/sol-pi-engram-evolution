description: 规格驱动开发。在写任何代码之前先写规格说明。适用于：启动新项目/功能、需求模糊、变更跨多个文件、做架构决策、任务超过30分钟。不适用于：单行修复、拼写错误、自包含的明确变更。Spec-Driven Development"没有规格的代码就是猜测。"核心理念规格说明是 AI 和人类工程师之间的共享事实来源。先定义做什么、为什么、如何衡量完成，再写代码。四阶段门控流程SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT   │          │        │          │   ▼          ▼        ▼          ▼ 人类       人类     人类       人类 审查       审查     审查       审查每个阶段必须通过人类审查后才能进入下一阶段。Phase 1: Specify（规格说明）先暴露假设在写规格内容之前，明确列出假设：我正在做的假设：1. 这是一个 Web 应用（非原生移动端）2. 认证使用 session cookie（非 JWT）3. 数据库是 PostgreSQL（基于现有 Prisma schema）4. 只面向现代浏览器（不需要兼容 IE11）→ 如果有误请纠正，否则我将按这些假设继续。六个核心规格领域目标 — 做什么、为什么、给谁、成功标准命令 — 完整的可执行命令（含参数）项目结构 — 目录布局及说明代码风格 — 展示约定的真实代码片段测试策略 — 框架、位置、覆盖率、测试层级边界 — 三级系统（总是做/先问/绝不做）规格模板# Spec: [项目/功能名称]## 目标[我们做什么以及为什么。用户故事或验收标准。]## 技术栈[框架、语言、关键依赖及版本]## 命令[构建、测试、lint、开发 — 完整命令]## 项目结构[目录布局及说明]## 代码风格[示例片段 + 关键约定]## 测试策略[框架、测试位置、覆盖率要求、测试层级]## 边界- 总是做: [...]- 先问: [...]- 绝不做: [...]## 成功标准[如何知道完成了 — 具体的、可测试的条件]## 待解决问题[任何需要人类输入的未决事项]将模糊需求重构为成功标准需求: "让仪表盘更快"重构后的成功标准:- 仪表盘 LCP < 2.5s（4G 网络）- 初始数据加载 < 500ms- 加载期间无布局偏移（CLS < 0.1）→ 这些目标对吗？Phase 2: Plan（计划）生成技术实施计划，涵盖：主要组件和依赖关系实施顺序（什么必须先构建）风险和缓解策略并行 vs 串行工作阶段间的验证检查点计划必须可审查 — 人类应能批准或要求修改。Phase 3: Tasks（任务拆解）将计划分解为离散的、可实施的任务：可在单次专注会话中完成每个任务有明确的验收标准包含验证步骤（测试、构建、手动检查）按依赖关系排序（非按感知重要性）单个任务不超过 ~5 个文件任务模板- [ ] 任务: [描述]  - 验收: [完成时必须为真的条件]  - 验证: [如何确认 — 测试命令、构建、手动检查]  - 文件: [会涉及哪些文件]Phase 4: Implement（实施）逐个执行任务，配合使用：planning-and-task-breakdown skill（增量实施）tdd skill（测试驱动）保持规格是"活文档"决策变更时更新规格 — 先更新规格，再实施范围变更时更新规格 — 在规格中反映增减提交规格 — 与代码一起存入版本控制PR 中引用规格 — 链接到每个 PR 实现的规格部分spec-kit 增强工作流（2026-06-15 深度集成）来源：GitHub 项目 github/spec-kit — 规范驱动开发框架
