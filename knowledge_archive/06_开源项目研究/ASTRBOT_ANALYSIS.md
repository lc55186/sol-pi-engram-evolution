## 核心机制

### 1. 渠道抽象层（适配器）

- WebUI 里为每个 IM 平台拨一个开关，一个控制台控制多个群聊机器人
- 企微有两种形态（应用 + 智能机器人）都在官方维护序列里
- 不用自己写长连接、消息去重、上下文管理、并发控制——官方替你扛了
- 省掉的不是初版的两周开发，是后面每一次平台改协议的跟着改

### 2. Agent 沙箱（v4.12.0+）

| 部件 | 作用 |
|------|------|
| **Bay** | 创建/管理沙箱的控制面 API |
| **Ship** | Python / Shell / 文件系统能力，文件系统固定在 `/workspace`、调用文件工具只能传相对路径（出不了这层墙） |
| **Gull** | 浏览器自动化 |

- 每个沙箱上限 **1 vCPU + 512MB 内存**
- 建议宿主机 **2 CPU / 4GB 内存 + 开启 Swap** 才能稳定并行跑多个实例
- 沙箱是给**单次任务用的轻量容器**，不是长期驻留服务

### 3. CUA 驱动器（点鼠标/敲键盘/看屏幕）

- 支持拉起 Linux / macOS / Windows / Android 镜像
- 统一暴露**截图 / 鼠标 / 键盘 / 文件系统**接口给 Agent
- 代价：宿主机需要容器或 VM 运行时，`cua` 包要单独安装（不在默认依赖里）

### 4. 子代理编排（v4.14.0，实验性）

- 主 Agent 增加一批 `transfer_to_<子代理名>` 委派工具
- 遇到不该管的任务就整包转交，子代理用自己挂载的工具干完再回传结果
- **核心亮点**：可以给子代理单独指定模型提供商——主 Agent 用大模型负责理解/规划，查天气、读文件这种简单活的子代理用便宜模型
- 这是在 Prompt 层面做**按需付费**，而不是在账单层面祈祷

### 5. 不站队的模型接入

- LLM 服务：OpenAI 兼容 / Anthropic / Gemini / Moonshot / 智谱 / DeepSeek——一视同仁
- 本地：Ollama / LM Studio
- 智能体平台整包接入：Dify / 阿里云百炼 / Coze——把对方编排好的应用当成本地的一条能力
- 往上还有一整套对话治理：知识库 + 人格设定 + MCP/Skills 扩展 + 自动上下文压缩

## 设计哲学（四句）

> 入口放在用户已有的地方，能力关进沙箱，扩展交给插件，模型选择权留给用户。

前两句决定了它好上手，后两句决定了它不会被某一个平台或某一家模型绑死。

## BOSS-AI-R 评估

### 哪些东西能直接借

| 东西 | 用法 |
|------|------|
| **渠道抽象层的思路** | BOSS-AI-R 未来要不要给老板提供"企业微信群里 @ 机器人 获取决策提示"的能力——这是个通路设计参考 |
| **子代理编排的模式** | 主模型（贵、强）负责理解和规划，子模型（便宜、快）负责查天气/读文件/跑脚本——这是个成本优化模式参考 |
| **沙箱隔离的思想** | 代码执行、文件读写类功能对接入安全性有要求——AstrBot 的"沙箱内固定 /workspace + 只能传相对路径"是个具体实现参考 |
| **插件市场的概念** | 未来 BOSS-AI-R 的"场景规则包"能不能做成插件式可插拔——AstrBot 的 1000+ 插件生态是一个验证案例 |

### 哪些东西不能直接用（因为方向不对）

- AstrBot 是**群聊机器人平台**，目标是 IM 渠道接入 + 聊天式交互
- BOSS-AI-R 当前是**APP（实时副驾 + 耳语提示 + 本地推理 + 声学情绪分析）**
- 两者的交互范式不同：一个是"群里 @ 机器人"，一个是"老板戴耳机/手表实时获得提示"
- AstrBot 本身不是 BOSS-AI-R 的直接组件——但它提供的**通路设计、成本优化、安全隔离三个思路**可以抽出来用

### 竞争/参考意义

- AstrBot 证明了"把 AI 入口放在用户已有的聊天工具里"是一个被大量真实部署撑住的方案
- BOSS-AI-R 的差异化是"实时耳语 + 纯本地推理 + 谈判垂直"，和 AstrBot 的"群聊机器人"不在同一个竞争点上
- 但 AstrBot 的 17 个 IM 渠道清单里有**企微 + 飞书 + 钉钉**——这对 BOSS-AI-R 未来可能需要的"企业侧场景规则包交付通路"有参考意义

## AGPL-3.0 风险（必须先想清楚）

- 自己用、内部部署：**没有额外约束**
- 把它包一层做成对外提供的闭源商业服务：**AGPL 的传染性条款需要提前让法务过一遍**
- 这类问题拖到上线前才发现，返工成本往往比换方案更高
- **对 BOSS-AI-R 而言**：AstrBot 本身不直接用在产品里（BOSS-AI-R 是自研 APP），所以 AGPL 传染风险较低；但如果未来要基于 AstrBot 做某个子模块或二次开发商用，就得法务评估

## 安装路径（三行）

```bash
uv tool install astrbot --python 3.12   # 首次安装
astrbot init                              # 仅首次，初始化环境
astrbot run                               # 跑起来

# 升级
uv tool upgrade astrbot --python 3.12
```

- 容器路线：仓库自带 Dockerfile + compose.yml，也可以走 Docker / Docker Compose
- 还有宝塔面板 / 1Panel 应用商店 / CasaOS 可视化部署（适合 NAS 和家庭服务器）
- AstrBot-desktop 桌面客户端 + astrbot-launcher（环境隔离多开）

---

## 两个坑（官方提前说的）

1. macOS 用户首次执行 `astrbot` 命令可能要等十到二十秒——是系统安全检查在扫描，不是卡死
2. 沙箱选 CUA 驱动器时，得先在 AstrBot 使用的 Python 环境里单独装 `cua` 包，否则启动沙箱时直接报依赖缺失（它不在默认安装列表里）

## 结论

1. **AstrBot 是一个成熟的群聊机器人统一控制台**（4万 Star、4年高频推进、15个官方维护渠道、1000+插件、沙箱 + 子代理编排已落地）
2. **它的价值对 BOSS-AI-R 是"思路参考"而不是"直接组件"**——渠道抽象、子代理按需付费、沙箱隔离这三个模式可以抽出来用，交互范式不对所以不直接集成
3. **AGPL-3.0 许可证**——自己用 / 内部部署没问题，闭源商业服务需要法务过一遍；BOSS-AI-R 自研 APP 路线直接用风险低，但万一未来二次开发商用得法务评估
4. **值得快速试跑一次**——10-20 分钟跑起来，看看控制台和消息流，给你一个直观的"群聊 AI 入口长什么样"的参照
