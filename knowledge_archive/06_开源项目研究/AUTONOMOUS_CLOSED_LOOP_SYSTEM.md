
# 自主闭环自治系统：自主决定 → 自动执行 → 自动反馈 → 自动优化 → 自动进化 → 自动决策 → 自动创新 → 自动升级

> 2026-09-23
> 基于 Sirchmunk（自进化知识库） + Laya-MLX（轻量本地判决） + SoL-Pi Engram（图谱记忆/自主演化引擎）

---

## 1. 闭环自治的本质

"自主" ≠ 无人监管，而是**系统能在无人干预下完成一套闭环任务，并在失败时自我修正**。

最小闭环定义：
```
输入 → 判决 → 执行 → 观测 → 反馈 → 调节 → 再执行
```

如果这个环能自我运转（哪怕只是简单规则），就是闭环自治。
如果这个环能自我改变规则（调整阈值、换路由、换模型），就是自主演化。
如果这个环能发明新任务、新能力、新组织方式，就是自主创新。
如果这个环能把新能力固化为新模块/新架构，就是自动升级。

---

## 2. 现有组件如何构成闭环

### 组件一览

| 组件 | 角色 | 闭环中的位置 |
|------|------|-------------|
| **Laya-MLX** (322M multilingual, 7.4ms) | 轻量结构化判决 | 输入 → 判决 |
| **Sirchmunk** (Indexless Retrieval + KnowledgeCluster) | 自进化检索/知识组织 | 检索 → 反馈 → 优化 |
| **SoL-Pi Engram** (自主演化引擎 RSI) | 模块热替换、A/B测试、模板进化 | 调节 → 进化 → 升级 |
| **图谱数据库** (SQLite Graph) | 结构化知识存储 | 执行的结果存储 |
| **todo_engine** (自主待办) | 任务识别、计划、执行追踪 | 输入任务 → 执行追踪 → 反馈 |
| **pipeline.py** (主入口) | 查询协调、多阶段串联 | 执行编排 |

### 最小可行闭环（MVP）

```
用户请求 / 定时事件
    │
    ▼
┌────────────────────────────────────────────────────┐
│ 【阶段1: 判决】Laya-MLX 轻量判断                     │
│ - 任务类型: choice(搜索型/结论型/都要)             │
│ - 紧急度: score(不急/一般/紧急)                    │
│ - 是否需要检索: noul(需要/不需要)                   │
└────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────┐
│ 【阶段2: 执行】按判决分路                               │
│ - 搜索型 → Sirchmunk 检索 + 合成                      │
│ - 结论型 → Laya-MLX 直接输出                           │
│ - 都要型 → Sirchmunk检索 + Laya过滤 + LLM综合        │
└────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────┐
│ 【阶段3: 观测 + 反馈】                                  │
│ - 任务完成了吗？成功/失败/部分                          │
│ - 用户后续 actions: 接受/修改/追问/忽略               │
│ - 耗时: 延迟是多少？                                    │
│ - 成本: LLM 调了多少 token？                            │
└────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────┐
│ 【阶段4: 优化】                                         │
│ - 反馈保存到 Sirchmunk KnowledgeCluster               │
│ - 失败模式聚类 → 调整判决规则 (阈值/路由)              │
│ - A/B 测试不同判决策略，保留更好的                       │
└────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────┐
│ 【阶段5: 进化】                                         │
│ - self_evolution.py: 模块热替换新判决规则               │
│ - 模板进化: 自动生成新 prompt 模板                       │
│ - 能力升级: 新的任务类型被识别 → 注册新模块              │
└────────────────────────────────────────────────────┘
```

## 3. 第一闭环：任务路由自主调整

### 背景

目前新任务进来时，固定走某种模式。随着任务类型的多样化，固定路由会越来越差。

### 闭环设计

1. **Laya-MLX 判任务意图**
   - choice: 这任务是"需要检索型"、"需要推理型"、"两者都要"？
   - score: 任务紧急程度如何？
   - noul: 这个任务是否太简单，不需要大模型？

2. **按判决结果走不同路由**
   - 检索型 → Sirchmunk 检索
   - 简单型 → Laya-MLX 直接结论
   - 复杂型 → Sirchmunk 检索 + LLM 合成

3. **记录执行结果 + 用户反馈**
   - 用户接受/修改/追问 = 反馈信号
   - 用户忽略/删除 = 负面信号

4. **自主演化引擎分析反馈**
   - 如果某类任务路由常导致用户修改 → 调整该类任务的路由规则
   - 如果某类任务简单路由能解决 → 增加该类任务的简单路由权重
   - 用 A/B 测试不同路由规则，保留效果更好的

5. **固化为新模板**
   - 调整后的路由规则作为新的判决模板
   - self_evolution.py 热替换到 pipeline 中

### 验证指标

| 指标 | 测量方式 |
|------|----------|
| 路由准确率 | 用户接受率 (接受/总任务) |
| 用户修改率 | 修改/总任务 (越低越好) |
| 任务完成延迟 | 首次响应时间 |
| LLM 成本 | token 消耗 |

## 4. 第二闭环：检索质量自主演化

### 背景

Sirchmunk 的 KnowledgeCluster 会自进化（搜索越多，聚类越丰富），但检索质量依赖LLM调用效果。

### 闭环设计

1. **每个检索请求产生一个 KnowledgeCluster**
2. **聚类内的文档片段由 Laya-MLX 评估相关性** (noul: 这片段和查询相关吗？)
3. **用户后续行为作为反馈** (点开了片段/忽略了片段/追问了同一问题)
4. **如果用户频繁忽略某类片段 → 调整该类片段的过滤规则**
5. **如果用户频繁点击某类片段 → 提升该类片段的权重**

### Laya-MLX 在这里的作用

```
检索片段 → Laya-MLX(noul: relevant?) → P(relevant) 
    → >0.7 的片段保留
    → <0.3 的片段丢弃 (省 LLM token)
    → 0.3-0.7 的片段标记待考察
```

### 验证指标

| 指标 | 测量方式 |
|------|----------|
| 片段点击率 | 点击片段/展示片段 |
| 检索满意度 | 用户是否重复同一查询 |
| LLM token 节省率 | 用 Laya 过滤前后 token 对比 |

## 5. 第三闭环：系统能力自我扩展

### 背景

随着系统运行，会遇到新类型的任务（当前组件不直接支持）。

### 闭环设计

1. **检测新任务模式**
   - todo_engine 记录新类型的任务
   - 聚类分析任务之间的相似性
   - 如果某类任务反复出现 → 标记为"新能力需求"

2. **评估已有组件是否能组合支持**
   - Sirchmunk 检索能否满足？
   - Laya-MLX 判决能否满足？
   - 组合这两个能否满足？还是需要新 LLM？

3. **如果组合现有组件能满足 → 自动创建"任务模板"**
   - 记录这个任务类型、需要的组件链、成功率
   - 注册到 pipeline 中

4. **如果需要新能力 → 触发自主创新流程**
   - 调研新技术（自动化搜索 + 评估）
   - 类似"Sirchmunk + Laya-MLX"的组合发现过程自动化

### 验证指标

| 指标 | 测量方式 |
|------|----------|
| 新任务类型识别率 | 新类型被识别为"模式"的及时性 |
| 能力扩展成功率 | 新模板创建并稳定运行的比例 |
| 技术引入回报 | 新技术带来的效能提升 |

## 6. 第四闭环：自主演化引擎驱动架构升级

### 背景

self_evolution.py 已有模块热替换、A/B测试、模板进化能力。

### 闭环设计

1. **模块热替换**: 不用重启，直接用新代码替换旧组件
2. **A/B 测试**: 新旧规则同时运行，比较效果，保留更好的
3. **模板进化**: 根据反馈自动生成新 prompt 模板
4. **晋升机制**: 表现好的模板自动晋升为默认

### 升级流程

```
新规则/新模板 → A/B 测试 (7天) → 效果更好 → 晋升为默认 → 老规则下线
```

### 验证指标

| 指标 | 测量方式 |
|------|----------|
| 模块热替换成功率 | 替换成功/尝试次数 |
| A/B 测试决策正确率 | 选择了更好规则的比例 |
| 模板进化次数 | 单位时间新模板生成数 |
| 架构升级次数 | 单位时间架构变更次数 |

## 7. 第五闭环：基于失败的自我纠正

### 背景

任何系统都会失败。闭环自治的关键是"失败时如何反应"。

### 闭环设计

```
失败事件
    │
    ├─→ 立即反应: 尝试修复/回退/降级
    │     - 例如: LLM API 失败 → 回退到 Laya-MLX 轻量结论
    │     - 例如: Sirchmunk 检索超时 → 回退到缓存结果
    │
    ├─→ 事后分析: 记录失败模式
    │     - 什么类型的失败？多久一次？
    │     - 哪个组件导致的？
    │
    └─→ 规则更新: 根据失败模式调整
          - 增加回退路径
          - 调整超时设定
          - 增加监控告警
```

### 示例

| 失败类型 | 立即反应 | 事后优化 |
|---------|---------|---------|
| LLM API 超时 | 回退到 Laya-MLX 结论 | 调整路由规则，类似任务优先用 Laya |
| Sirchmunk 检索超时 | 返回缓存/空结果 | 调整超时阈值，增加分片检索 |
| 用户频繁拒绝结果 | 记录拒绝模式 | 调整判决规则，减少该类结果输出 |
| 任务完成质量低 | 用户修改/追问 | 调整任务模板，增加步骤或换组件 |

## 8. 第六闭环：知识库自我组织（Sirchmunk 原生）

### 背景

Sirchmunk 的 KnowledgeCluster 自进化是其原生能力。

### 闭环运作

1. **每次查询构建或更新一个 KnowledgeCluster**
2. **相似查询命中现有聚类 → 直接返回，更快**
3. **聚类之间合并 → 形成元社区**
4. **热度变化 → 调整聚类权重**
5. **长期积累 → 自动形成知识图谱结构**

### 这个闭环是"数据驱动的自我组织"

不需要显式编程，系统用得越多，知识组织越好。

## 10. 实施优先级

### P0: 最小闭环（2周）

**目标**: 跑通"判决 → 执行 → 反馈 → 简单调节"这一环

1. Laya-MLX 接入 pipeline，作为任务意图判决器
2. Sirchmunk 接入，作为文档检索层
3. 反馈收集: 用户接受/修改/忽略记录
4. 简单调节: 根据接受率调整路由权重

### P1: 检索自进化闭环（4周）

**目标**: 检索结果质量随使用自动提升

1. Laya-MLX 片段相关性评估接入
2. 用户片段点击反馈收集
3. 片段过滤规则自动调整
4. KnowledgeCluster 质量指标追踪

### P2: 任务路由自主演化闭环（6周）

**目标**: 路由规则随使用自动优化

1. 任务类型分类模板化
2. A/B 测试不同路由策略
3. 路由规则热替换
4. 用户修改率作为核心优化指标

### P3: 能力自我扩展闭环（8-12周）

**目标**: 系统能识别新任务类型并扩展能力

1. 新任务模式自动识别
2. 现有组件组合支持评估
3. 新任务模板自动创建
4. 技术引入评估自动化触发

### P4: 架构进化闭环（持续）

**目标**: 系统架构随能力扩展自动演化

1. 模块热替换常态化
2. A/B 测试驱动架构决策
3. 旧组件自动清理
4. 自主演化速度可控（防止过快变异）

## 11. 验证体系

### 核心指标仪表板

| 指标类别 | 具体指标 | 目标 |
|---------|---------|------|
| **自治度** | 无人干预完成任务比例 | >80% |
| **自愈能力** | 失败后自动恢复比例 | >90% |
| **进化速度** | 单位时间规则优化次数 | 月 10+ 次 |

### 观测手段

1. **日志追踪**: 每次闭环运行记录完整轨迹
2. **反馈信号追踪**: 每条反馈关联到导致它的判决/执行
3. **规则版本追踪**: 每个规则变更记录原因和效果
4. **仪表板**: 实时展示闭环健康状态

## 12. 风险与边界

### 风险

1. **闭环失控**: 优化方向错了，系统向错误方向进化
   - 缓解: 保证反馈信号质量，增加人工审核节点（偶尔抽查）

2. **过度优化**: 系统过度适应特定用户，失去通用性
   - 缓解: 多用户反馈 pooled，定期重置极端优化

3. **进化速度失控**: 变化太快，系统不稳定
   - 缓解: 进化速度限制（每周最多 N 次规则变更）

4. **新能力错误扩展**: 自动识别的新任务模板效果差
   - 缓解: 新模板经过 A/B 测试后才固化

### 边界

- **自动做的事**: 判决、路由、检索增强、片段过滤、反馈收集、规则调整、模块热替换
- **需要人工确认的事**: 架构大变更、新组件引入、外部 API 接入、费用相关变更
- **自动不做的事**: 不会自动删数据，不会自动改变安全规则，不会自动花钱

## 14. 结论

1. **"自主决定"**: 由 Laya-MLX 轻量判决 + Sirchmunk 检索结果共同决定下一步动作
2. **"自动执行"**: pipeline 根据判决结果走不同组件链
3. **"自动反馈"**: 用户行为、系统指标、失败事件三源反馈
4. **"自动优化"**: 基于反馈调整路由权重、片段过滤规则、判决阈值
5. **"自动进化"**: self_evolution.py 热替换、A/B测试、模板进化
6. **"自动决策"**: A/B测试的结果决定保留哪个规则
7. **"自动创新"**: 新任务模式识别 → 组件组合 → 新模板创建
8. **"自动升级"**: 新组件注册到 pipeline，旧组件下线，架构微调

**闭环的本质**: 系统自己完成了"尝试 → 观察 → 学习 → 调整 → 再尝试"的全过程。
