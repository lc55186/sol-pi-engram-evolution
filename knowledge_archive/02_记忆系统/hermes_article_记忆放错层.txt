标题: Hermes 变傻，不是它忘了，是你把记忆放错层了
Article ID: 7634761015737041460

> 系列第一篇：诊断 + 止血。
大家可以先判断自己是不是中招。

“太烦了！”
这是一个网友在留言里说的原话。
他说自己已经被 Hermes Agent 无限压缩的记忆搞到烦躁：前面刚讲清楚的规则，后面又乱了；刚确认过的项目背景，过一会儿又像没看过；更要命的是，它不是彻底失忆，而是记住一半、丢掉一半。
这种状态最折磨人。
因为你没法判断：到底是模型不行，还是工具出 bug，还是自己用法不对。
我的判断是：很多时候不是 Hermes 突然变傻，而是记忆被放错层了。
Hermes 不是只有一个“记忆”。
它至少有四层：当前会话上下文、内置长期记忆、历史会话检索、外挂记忆 Provider。
很多人把这四层全当成 MEMORY.md 一件事。
于是就会出现一个很典型的灾难：什么都往温记忆里塞，项目背景、个人偏好、临时任务、历史过程、调试日志、甚至整段方案都往里写。
等它满了，或者会话长到触发压缩，模型开始做有损摘要，任务逻辑自然就开始断。
所以，我们先把病根拆清楚。
一、Hermes 的记忆不是一层，而是四层
如果你只记住一句话，就记住这句：
MEMORY.md 不是知识库，更不是项目数据库。它只是一个很小的常驻提示区。
Hermes 的记忆可以粗略分成四层。
第 1 层：热记忆，当前会话上下文
这是最容易被误解的一层。
你和 Hermes 当前这轮对话、它刚读过的文件、刚执行过的命令、刚拿到的工具输出，都在这里。
它看起来最聪明。
因为上下文还热，前后连贯，短时间内它确实像“什么都记得”。
但热记忆有一个硬限制：会话越长，成本越高，也越容易触发压缩。
Hermes 默认有自动上下文压缩机制。配置里能看到类似这样的项：
compression:  enabled: true  threshold: 0.50      # 默认接近上下文 50% 时触发压缩  target_ratio: 0.20   # 保留尾部上下文预算比例  protect_last_n: 20   # 保护最近若干消息这不是 bug。
这是为了防止上下文爆掉。
真正的问题在于：压缩本质上是摘要，摘要就一定有损。
如果前面会话里有大量临时日志、废话、重复要求、长工具输出，压缩器会尝试把它们变成一个较短的交接摘要。
一旦摘要没有保住关键因果链，后面的 Agent 就会开始“看似继续，实际跑偏”。
第 2 层：温记忆，MEMORY.md和 USER.md
这一层是很多人踩坑的核心。
Hermes 的内置长期记忆主要是两个文件：
文件
适合放什么
默认建议上限
~/.hermes/memories/MEMORY.md
环境事实、项目约定、工具经验
约 2200 字符，约 800 token
~/.hermes/memories/USER.md
用户偏好、沟通风格、稳定要求
约 1375 字符，约 500 token
这两个文件会在新会话开始时注入系统提示词。
注意，是“新会话开始时”。
它有一个很重要的机制：会话启动时读取一次，形成冻结快照。
也就是说，你在当前会话里让 Hermes 写入了新的 memory，文件会更新，但这条新记忆通常要到下一个会话才会真正进入系统提示区。
这就是很多人困惑的地方：
“我明明让它记住了，为什么它下一句还是没用上？”
原因可能不是没写入，而是当前系统提示快照没有刷新。
另外，温记忆很小。
它不是给你塞长文档的。
它最适合放这种短句：
用户偏好：默认中文回复，结论前置，技术内容优先分点。项目约定：当前 APP 项目在 /mnt/d/dev_work/projects/fishapp。协作边界：涉及删除、覆盖、迁移前必须先确认。它不适合放这种东西：
某次调试完整过程、长篇需求文档、接口返回样例、几十条临时 TODO、整篇文章大纲、完整项目 README。把这些塞进去，只会挤爆常驻提示区。
更糟的是，模型会被迫在“保留什么、删掉什么、合并什么”之间做选择。
这就是很多记忆割裂的开始。
第 3 层：冷记忆，SQLite + FTS5 的历史会话检索
Hermes 会把历史会话写入 SQLite。
底层有 FTS5 全文检索能力。
这层不是常驻记忆。
它更像一个可以搜索的档案柜。
你不问，它通常不会自动翻。
适合放在这一层的内容是：过去某次讨论、某个历史决策、某次排障细节、某个已经结束的任务过程。
你可以通过会话检索找回来，例如：
hermes sessions list在 Agent 任务中，也可以让它用 session_search 查过去会话。
但这里有个现实问题：FTS5 是全文检索，不是读心术。
你问得太泛，它可能搜不准。
比如：
上次那个问题怎么解决的？这就不如：
搜一下 fishapp 里“登录接口 401”和“token 刷新”的历史会话。冷记忆能救命，但前提是关键词给对。
第 4 层：外挂记忆，Memory Provider
外挂记忆，我后续会单独去讲，这里先不展开。
Hermes 现在支持外部 Memory Provider。
官方文档里列过多种 Provider：Honcho、OpenViking、Mem0、Hindsight、Holographic、RetainDB、ByteRover、Supermemory 等。
这层的价值在于：它不再把所有东西都塞进 MEMORY.md 那个小窗口，而是用外部系统做长期存储、语义检索、实体关系、知识树或本地数据库。
配置入口很简单：
hermes memory setuphermes memory status也可以手动配置：
memory:  provider: holographic  # 示例：也可以是 hindsight、openviking、byterover 等但有两个边界要记住：
内置 MEMORY.md / USER.md 仍然存在；外挂 Provider 是增强，不是直接替代。
当前机制通常只允许一个外部 Provider 同时激活，避免工具膨胀和记忆后端冲突。
这里我就先不展开讲了。
你只要先知道：真正的长期知识，不应该全部靠 MEMORY.md 扛。
二、为什么它会“变傻”：核心病根就四个

Hermes 变傻，通常不是一个单点问题。
我更愿意把它看成四个问题叠在一起。
1. 把 MEMORY.md当知识库
这是最常见的用法错误。
MEMORY.md 只有两千多字符的建议容量。
它应该写“稳定规则”，不是写“过程材料”。
什么是稳定规则？
比如：
用户默认中文回复
删除文件前必须确认
项目目录在哪里
测试命令是什么
某个工具有已知坑
什么是过程材料？
比如：
今天调试了哪些报错
某次文章写到第几段
某个接口返回了什么大 JSON
一次聊天里的全部推理过程
过程材料应该放项目文件、会话历史或外部 Provider。
不该放温记忆。
2. 会话太长，触发有损压缩
Hermes 的压缩器会保护开头和最近一段上下文，中间内容会被摘要。
这个设计合理。
但摘要不是复制。
如果你在一个会话里连续做了太多事：写文章、改代码、跑测试、讨论配置、再调 UI、再让它记住偏好，最后它要把一堆复杂链路压成一段交接说明。
这时很容易丢掉“为什么这么做”。
它可能记得结果，却忘了原因。
也可能记得任务，却忘了约束。
于是后面就会出现一种很烦人的状态：它不是完全胡说，而是半对半错。
3. SOUL.md、规则文件和工具太重
很多人喜欢把人格设定写得很长。
像这样：
你是一位兼具工程师、产品经理、架构师、作家、战略顾问、心理咨询师、商业分析师能力的超级助手……这类内容看起来很燃。
但对工程任务帮助不大。
更大的问题是：它会挤占上下文预算。
SOUL.md 应该短、硬、可执行。
推荐控制在 300-600 字以内。
一个更实用的版本是：
# SOUL.md你是我的工程与写作助手。工作原则：- 结论前置，短句优先。- 不确定先查，不瞎编。- 技术任务先验证，再汇报。- 删除、覆盖、迁移前必须确认。- 不把临时过程写入长期记忆。- 重要配置给最小可用样例。这就够了。
不要把角色设定写成小作文。
工具也是一样。
如果你只是让 Hermes 做一个本地代码排障任务，就没必要一次性加载所有工具集。
命令行里可以考虑只启用必要工具集：
hermes chat -t terminal,file如果需要联网再加 web：
hermes chat -t terminal,file,web工具越多，系统提示越膨胀，模型越容易被无关能力分散。
4. 以为冷记忆会自动想起来
很多人以为：既然 Hermes 有历史会话，那它一定能自动想起所有历史。
不是。
冷记忆更像搜索引擎。
你要给关键词。
比如你想让它找过去某个项目决策，不要问：
我们之前怎么定的？最好问：
请用 session_search 搜索 “fishapp 页面风格” 和 “鸿蒙 ArkTS 组件规范”，找之前定过的约束。关键词越准，召回越稳。

三、先判断自己是不是中招
你可以对照这张清单。
如果中了 3 条以上，基本就该止血了。
它反复忘记你已经强调过的边界。
它开始把旧任务和新任务混在一起。
它知道项目名，但说错路径。
它记得要做 A，却忘了为什么不能做 B。
它开始重复读取文件、重复跑同一类检查。
它给出的总结越来越像“压缩摘要”，没有因果链。
它把临时结论当成长期规则。
它开始主动脑补你没说过的配置。
它说“我已经完成”，但实际文件没落盘。
它在长会话后突然变得很自信，但细节错得离谱。
这种时候，不要继续硬聊。
你越继续，它越可能把错误状态再压缩进去。
四、10 分钟止血：先把当前任务救回来

这里给一套最小动作。
不是最优雅，但最能立刻止损。
动作 1：用 /new重开会话
如果你已经明显感觉它乱了，直接：
/new或者：
/reset这会开启一个新会话，清掉当前会话历史，重新加载系统提示、项目上下文和内置记忆。
代价也很明确：当前对话上下文没了。
所以不要裸重启。
重启前先让它输出一段交接摘要：
请用 10 条以内总结当前任务状态：目标、已完成、未完成、关键文件、不能改的边界、下一步验证命令。不要展开解释。复制这段摘要。
然后 /new。
新会话第一句直接贴：
接着这个交接摘要继续，不要重新发散。先核对文件状态，再做下一步。这比硬撑一个已经压坏的长会话更稳。
动作 2：用 /compress <focus>手动压缩
如果你还不想重开，可以先手动压缩，并指定重点。
比如：
/compress 当前 fishapp 登录问题、关键文件路径、接口 401 根因、下一步验证命令它的意义是：告诉压缩器“这部分别丢”。
这不保证 100% 不丢信息，但比默认压缩要好。
尤其适合这种场景：
会话很长
任务还没结束
你知道最关键的信息是什么
不想马上丢掉当前上下文
动作 3：临时关掉内置温记忆，排除干扰
如果你怀疑 MEMORY.md 或 USER.md 已经污染了任务，可以先做一次“干净会话”验证。
配置里可以临时关掉内置记忆：
# ~/.hermes/config.yamlmemory:  memory_enabled: false  user_profile_enabled: false然后开新会话再试。
如果关掉后明显变正常，说明你的温记忆里很可能有过期、冲突或过长内容。
注意：
hermes memory off这个命令主要是关闭外部 Provider，让系统回到 built-in only。
它不是关闭 MEMORY.md / USER.md。
如果你要关内置温记忆，看的是 memory_enabled 和 user_profile_enabled。
还有一点要特别提醒：
我不建议直接写类似下面这种命令，除非你确认自己的版本支持并且你自己清楚的知道你要做什么：
HERMES_WARM_MEMORY_OFF=1 hermes "任务描述"在当前可核验的命令和配置里，我没有把它当成通用官方入口。
如果这是你自己封装的环境变量，可以在团队内部用。
对我们大部分用户来说，最好用 config.yaml 这种确定存在的配置方式。
动作 4：检查 MEMORY.md和 USER.md是否超载
先看字符数：
wc -m ~/.hermes/memories/MEMORY.md ~/.hermes/memories/USER.md如果 MEMORY.md 已经接近 2200 字符，USER.md 已经接近 1375 字符，就别再往里塞了。
该删删，该合并合并。
建议按这个规则清理：
保留：
稳定偏好
长期项目路径
常用验证命令
高风险边界
工具已知坑
删除：
已完成任务流水
临时 TODO
某次排障过程
长段文章大纲
可以从项目文件查到的内容
如果要手动编辑，先备份：
cp ~/.hermes/memories/MEMORY.md ~/.hermes/memories/MEMORY.md.bakcp ~/.hermes/memories/USER.md ~/.hermes/memories/USER.md.bak再编辑。
不要一上来全删。
动作 5：把长期材料放回正确位置
最关键的不是删，而是搬。
按这个表搬：
内容
应该放哪
沟通风格
USER.md
项目路径、固定命令
MEMORY.md
当前任务进度
当前会话交接摘要
项目规范
AGENTS.md
/ 项目文档
长篇设定 / 大纲
专门的项目文件
历史排障过程
SQLite 会话历史 / session_search
大量长期知识
外部 Memory Provider
你会发现，真正应该放进 MEMORY.md 的东西非常少。
这才是正确状态。
五、给一份更稳的最小配置
如果你现在已经被记忆问题搞烦了，可以先用这份保守配置。
# ~/.hermes/config.yamlcompression:  enabled: true  threshold: 0.40  target_ratio: 0.20  protect_last_n: 20memory:  memory_enabled: true  user_profile_enabled: true  memory_char_limit: 2200  user_char_limit: 1375  provider: ""解释一下：
threshold: 0.40
：比默认 0.50 更早触发压缩，避免等上下文太臃肿才处理。
target_ratio: 0.20
：保留一段近期尾部上下文，不让最近任务被压掉。
protect_last_n: 20
：尽量保护最近消息。
provider: ""
：先不用外部 Provider，排除变量。
如果你要做复杂长期任务，再考虑打开外部 Provider。
比如本地优先可以看：
hermes memory setup      # 选择 holographic / hindsight / openviking / byterover 等hermes memory status六、SOUL.md应该写短，不要写满
SOUL.md 是身份与行为原则。
它很重要，但不能臃肿。
我建议只写三类内容：
你是谁。
你怎么做事。
哪些事不能做。
示例：
# SOUL.md你是我的工程与写作助手。默认行为：- 结论前置。- 短句优先。- 技术任务给验证方案。- 不确定就查，不要猜。- 删除、覆盖、迁移前必须确认。记忆规则：- 只保存长期稳定事实。- 不保存临时任务流水。- 项目细节优先写入项目文档。这比写一大段“超级智能体人格”有用得多。
因为 Agent 真正需要的是可执行约束，不是角色表演。
七、结论
Hermes 的记忆问题，先别急着怪模型。
很多时候，问题根源是分层错了。
一句话总结：
热记忆负责当前连续性，温记忆负责少量稳定事实，冷记忆负责历史检索，外挂记忆负责长期知识。
不要让 MEMORY.md 扛所有事。
它扛不住。
如果你现在已经中招，今天先做三件事：
长会话乱了，先 /compress <focus> 或 /new。
检查 MEMORY.md / USER.md 是否超载。
把临时过程、长文档、项目资料搬出温记忆。
下一篇，我们讲“Hermes 记忆调优”。
重点不再是救火，而是把配置调稳：压缩阈值、工具加载、SOUL.md 长度、项目规则文件、外部 Provider 接入边界，全部给最小可用配置。
如果你已经被 Hermes 的记忆压缩搞崩过，可以先问自己一个问题：
你到底是想让它记住规则，还是想让它记住整个世界？
这两个需求，不能放在同一层里解决。
